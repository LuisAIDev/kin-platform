# ADR-044: Validación XSD MinSalud - Streaming SAX + Schemas desde S3

## Contexto
KIN Billing debe generar archivos RIPS (AF, AC, AP, AU, US, AT) que cumplan estrictamente con los esquemas XSD oficiales publicados por MinSalud (versión 2024). Los esquemas cambian periódicamente y la validación debe ser:
- Rápida (archivos de 10k-100k registros)
- Precisa (reportar errores por fila/campo)
- Actualizable sin redeploy (nuevas versiones XSD)

## Decisión
Implementar **validación XSD via streaming SAX** con **schemas versionados en S3 (bucket Bogotá)**.

### Arquitectura

```text
XsdValidator (Spring Component)
├── SchemaCache (Caffeine, TTL 24h)
│   └── Key: "rips_<type>_v<version>" → Schema compilado
├── S3SchemaLoader
│   └── Descarga schemas desde s3://kin-billing-schemas-colombia/minsalud/2024/
└── StreamingValidator (SAX)
    ├── Valida registro a registro (no carga todo en memoria)
    └── Reporta errores: fila, campo, mensaje
```

### Flujo de Validación

1. **Generación** → `RipsGenerationOrchestrator` genera batch + records
2. **Validación XSD** → `XsdValidator.validate(batch)`
   - Obtiene schema compilado del cache (o descarga de S3)
   - Itera `rips_records` ordenados por `sequence_number`
   - Convierte cada `rips_line_data` (JSON) → XML línea
   - Valida con `Validator.validate(StreamSource)`
   - En error: marca record `validation_status=INVALID`, guarda mensaje
3. **Validación Negocio** → `BusinessRuleValidator.validate(batch, context)`
4. **Resultado** → Batch `VALID` o `INVALID` con errores agregados

### Gestión de Schemas

| Aspecto | Implementación |
|---------|----------------|
| **Almacenamiento** | S3 bucket `kin-billing-schemas-colombia` (región `sa-east-1` / Bogotá) |
| **Estructura** | `minsalud/2024/rips_af.xsd`, `rips_ac.xsd`, ..., `rips_at.xsd` |
| **Versionado** | Prefijo `v2024/`, `v2025/` etc. |
| **Cache** | Caffeine `Cache<String, Schema>` TTL 24h, max 50 entries |
| **Hot-reload** | Endpoint admin `POST /admin/billing/schemas/reload` limpia cache |
| **Fallback** | Schema embebido en JAR (`classpath:schemas/minsalud/2024/`) si S3 falla |

### Esquemas XSD Oficiales MinSalud 2024

| Archivo | Tipo RIPS | Descripción |
|---------|-----------|-------------|
| `rips_af.xsd` | AF | Archivo Factura (cabecera) |
| `rips_ac.xsd` | AC | Consultas |
| `rips_ap.xsd` | AP | Procedimientos |
| `rips_au.xsd` | AU | Urgencias |
| `rips_us.xsd` | US | Usuarios (pacientes) |
| `rips_at.xsd` | AT | Otros Servicios |

### Manejo de Errores

```java
record ValidationError(
    int row,
    String field,
    String message,
    String xpath
) {}

record ValidationResult(
    boolean valid,
    List<ValidationError> errors
) {}
```

- **Errores XSD**: fila, campo XPath, mensaje original del validador
- **Errores Negocio**: fila, regla violada, valores esperados vs actuales
- **Agregación**: `RipsBatch.validation_errors` (JSONB) para auditoría completa

### Performance

| Métrica | Target |
|---------|--------|
| Validación 10k registros | < 5 segundos |
| Memoria pico | < 100 MB (streaming) |
| Cache hit rate | > 99% (schemas cambian raramente) |
| Cold start (descarga S3) | < 2 segundos |

### Seguridad

- Bucket S3: **solo lectura** para rol `kin-billing-reader`
- Schemas firmados con checksum SHA-256 verificado al cargar
- Sin ejecución de código externo (solo validación XML Schema 1.0)

## Consecuencias

### Positivas
- **Cero downtime** para actualizar schemas (subir a S3 → limpiar cache)
- **Streaming** = memoria constante independiente del tamaño del archivo
- **Trazabilidad completa**: cada error vinculado a `rips_record` específico
- **Versionado explícito**: `v2024`, `v2025` conviven; migración gradual

### Negativas
- **Dependencia S3** en runtime (mitigado: fallback a classpath)
- **Complejidad JSON→XML** por tipo RIPS (mitigado: builders por tipo)
- **Costo S3** mínimo (GET infrecuentes por cache)

## Alternativas Rechazadas

| Alternativa | Por qué No |
|-------------|------------|
| Validar con DOM (cargar todo en memoria) | OOM en archivos > 50k registros |
| Schemas embebidos en JAR | Requiere redeploy por cada cambio MinSalud |
| Validación solo en aplicación (sin XSD) | No garantiza cumplimiento normativo |
| Librería externa (xmlbeans, jaxb) | Dependencias pesadas, streaming limitado |

## Validación

- Test de integración: generar lote 3 contratos sintéticos → 100% XSD válido
- Test de performance: 10k registros US → < 3s validación
- Test de hot-reload: subir nuevo XSD a S3 → `POST /admin/schemas/reload` → validación usa nuevo schema
- Test de fallback: apagar S3 → validación usa schema embebido
